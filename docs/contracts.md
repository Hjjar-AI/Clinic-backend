# Models and API contracts

Django/DRF features live in `apps/`, shared infrastructure in `core/`, configuration in `config/`. Services own validation/lifecycle; serializers adapt representation; endpoint action permissions and shared record scope are both required. Current source is authoritative. [Operations](operations.md), [evidence](doneCurrent.md), [remaining work](workCurrent.md).

## Shared boundaries

- API `/api/v1/`, session credentials and config CSRF bootstrap. Unsafe requests send `X-CSRFToken`; JSON `data`/`error` envelopes preserve falsy data. Downloads are files; 204/205/304/replays have empty bodies.
- Mutations require positive integer opening `version`/quoted `If-Match`; bool/float coercion and conflicting header/body are rejected. Retain payload/key across uncertain retries; refresh conflicts. Ordinary reservation/mutation/receipt commit together, expire after 30 days, and replay only after current action/resource authorization.
- Patient scope combines effective dated care team and retained historical-author/creator scope; legacy doctor is display/create compatibility only. Backend effective grants, not admin role alone, determine actions; inactive users denied. User creation does not rewrite existing role grants.
- Patient-before-visit locking and post-lock scope/permission rechecks protect encounter changes. Login/password recovery lock current accounts; failed-attempt bookkeeping commits before auth failure; security changes revoke sessions. Signing/issuance require authorized clinician/edit permission. Critical signing, issuance, billing and merge service boundaries re-read active actors/effective grants; cached request actors cannot retain revoked role authority.
- Model cache ownership is declared once; raw recovery skips ordinary signals and explicitly invalidates its groups. Audit registration derives from its field allowlist; added patient-register entries record lifecycle/actor/reference metadata, leaving clinical text in protected domain history.
- DB-backed `CacheGeneration` commits with mutation; cache outages degrade to misses without deleting successful receipts. Installation-local `RecoveryOperation` has no restored-account FK and is excluded from replacement inventory. [Recovery protocol](operations.md#recovery).

## OS runtime boundary

The same service/API source targets modern Windows x64 and Linux with the declared Python dependencies. PostgreSQL retains session advisory gates; other profiles use Portalocker shared/exclusive file locks, including the Windows `win32` extra, on a common capable filesystem. Missing locking/native components fail closed. Waitress `serve` performs runtime/source checks without schema/seeding; dependency diagnosis is database-free. Native MIME/PDF loading honors explicit Windows DLL paths, MIME database and PDF font directory; MIME detectors with an explicit database are thread-local. Platform-specific installation does not weaken permissions, idempotency, signed evidence or production DB/cache requirements. Windows/macOS execution and network filesystem semantics require their own verification.

## Patient identity and ownership

Names are required; birth is optional year-only, gender/ID/phone may be unknown. `patient_number` is permanent and unique. Shared duplicate identifiers/phones warn nonblockingly without suffix changes. Completeness is a configurable recommendation, not validity: birth/gender/registration by default; optional ID/phone/team/language.

| Owner | Facts / invariants |
| --- | --- |
| Patient | Current names/year/gender, registration (`admission_date` alias), controlled marital status, optional occupation/address/phone/contact preferences. `national_id` projects blank-issuer/blank-country national ID. Identity verification actor/time are server-controlled and invalidated by changed identity. |
| PatientIdentifier | Type/value/issuer/uppercase two-letter country; unique active tuple within patient, duplicates across people allowed. Profile synchronization uses the complete compatibility tuple. |
| PatientContact | Person/relationship/phone/email/emergency/primary/notes; multiple contacts, at most one active primary. Active primary emergency contact owns legacy emergency fields; profile and register edits share versioned correction history. Projection validates the patient field bounds before persisting the parent; overflow rolls back the correction. |
| PatientRepresentative | Separate identity/contact, authority/evidence/verification/validity; recorded representation does not grant login access. |
| PatientCareTeam | Role doctor/nurse/therapist/assistant/coordinator, start/end/assigner/remover/reason; scope, displayed names and completeness use the same effective query. Unended planned memberships reserve the user/patient pair; cancellation ends no earlier than the planned start. Ended/rejoined rows retained. Nonadmin creators join team; admin selection need not add admin as clinician. |
| PatientAllergy / PatientMedication | Longitudinal substance/reaction/severity or drug/dosage/schedule/status/dates, source/provenance/visit/notes. Clinical-edit permission; positive evidence copies summary to recorded, retirement never silently asserts none-known. Unknown/negative summaries cannot contradict active positives; any changed summary requires clinical-edit, unchanged echoes allowed. |
| PatientFollowUp | Title/optional effective-team owner/due date, pending/completed/missed/cancelled/waived; server outcome actor/time, reason and same-patient visit/appointment/evidence. Newly attached completed visit must be active final/locked with approved revision; historical references retained. |
| PatientDocument | Protected uploaded bytes/checksum/MIME/size, category/description/date/source/provider, server verification and opening document version. Archive retains bytes; direct metadata lifecycle writes use canonical service. |
| PatientCorrection | Immutable actor/time/reason/before-after for profile/register changes. Family history/important notes require clinical-edit permission and clinical-view access to their correction history. |
| PatientDuplicateReview / PatientMerge | Ordered pair/reviewer/decision; immutable explicit merge manifest with original ownership/content/team/adjustments. |

Mutable register records retain creator/updater/times and active/retired actor/time/reason. Edits/retirement need reason; unknown fields/invalid links/choices/dates are rejected. `PatientFollowUp` owns every occurrence, including due date, optional method (In-person/Telehealth/Phone), outcome and terminal actor/time/reason. Terminal outcomes, schedule and completion evidence cannot be rewritten or reopened; identical record edits are no-ops. Scheduling after a terminal result creates another occurrence and retains the old row. Reports count active canonical occurrences once.

`Visit.follow_up` is an optional unique protected pointer to its current occurrence; the occurrence's `source_visit` retains provenance. There are no mirrored visit follow-up columns or bridge flag. Visit reads expose nested `follow_up`; writes accept `follow_up_input: {due_date, method, reason}`. An unchanged echo is a no-op. Changing/removing an existing plan requires reason; removing a pending plan retires its occurrence and detaches the pointer, while removing a terminal selection retains its result. Outcomes and additional actions use the patient register endpoint; there is no visit completion endpoint. Register writes lock patient → linked visit → occurrence, advance the patient version and the linked visit version, and detach a retired current occurrence. Visit-originated writes retain the calling action's permission; direct register edits require clinical edit permission and patient access. Signed revisions retain sign-time follow-up facts independently of later operational changes. Recovery validates pointer uniqueness, same-patient/source ownership, active occurrence and date bounds against the authenticated inventory.

## Patient API and reconciliation

Under `/patients/{id}/`:

| Endpoint | Contract |
| --- | --- |
| `records/` GET | `kind`, offset; identifiers/contacts/representatives/allergies/medications/follow-ups → `{items,total,version}`, 100/page including retired history. |
| `records/` POST | `{kind,record_id?,operation:save/retire,fields,reason,version}` → `{record,version}` using opening patient version. |
| `corrections/` GET | Offset, `{items,total,merges}`; 100 corrections/page/latest 100 merges, original merged-source history retained. Clinical changes require clinical-view permission. |
| `duplicate_review/` POST | `{other_id,status:dismissed/different,reason,version}`; review is optional/dismissible and matches can be shown again. |
| `merge_preview/`, `merge/` POST | Source URL, target ID → token; execute token/reason/source+target versions. Admin with edit/archive permissions, explicit consent; preview 10 minutes, binds actor/both versions/source content/team/access impact. |
| Care team / documents | `team_candidates/` minimal eligible users; team writes use patient version/removal reason, documents use their own opening version. |

Merge locks parents in stable order and rejects changed preview, including membership role/start/end changes. Transferred planned memberships keep their future start and confer no early access. Active survivor demographics remain; current records/visits/appointments/invoices/documents move, teams explicitly combine, duplicate active identifier tuples transfer retired, source primary contacts transfer nonprimary. Access broadening/history stays visible; source archives and links to survivor, merged source restoration is blocked. Signed revisions/issued bytes and immutable original ownership never rewrite. No automatic merge/undo contract.

## Encounters, documents and operations

Visit owns working encounter narrative, diagnoses/medications/labs/scales and attachments. Draft/final/amended/locked transitions use versions/reasons. Final signing creates immutable schema-v3 `VisitRevision`: identity/file number, longitudinal summaries/records, clinician/time, clinical rows/labs, scale definitions/answers, attachment inventory and a root `follow_up` snapshot. Catalog retirement cannot erase saved labels/controlled flags or scale snapshots. Scores/defaults must be finite, ranged and absolutely step-aligned; new active scales max 100 questions.

`IssuedDocument` is the sole issued-signature history and retains exact PDF/checksum/revision/actor/snapshot/signature/stamp; no separate prescription-signature model or write remains. Durable issuance validates embedded signature/stamp images (prescription signature required); prescription/referral require final/locked signed revision and block unsigned amendment issuance. Final persistence locks parent/visit, checks scope, visit/revision and preview patient version. Prescription issuance is orchestrated by its service; prescription/referral bytes and issuance audit share a transaction. Prescription preview removal runs only after commit and cache cleanup failure does not undo successful issuance. Clinical encounter dates and prescription age come from the approved revision; current address/clinic configuration remain explicit issue-time facts. History GET `/visits/{id}/revisions/` and `issued-documents/` is read-only. General patient/visit exports read current facts; working copies are labelled unapproved and suppress old signing metadata. Clinical unknowns remain distinct from false/zero: care setting and unknown/voluntary/involuntary `care_basis` are separate.

Optional prescription POST `print_options` selects `mode: blank/preprinted`, `width_mm` (80–216), `height_mm` (120–350), and `offset_x_mm`/`offset_y_mm` (−5…5, positive right/down); finite values have at most two decimals. A6 (105×148) is the UI/default-options size; omitted options retain the legacy A4 API renderer. Blank offsets normalize to zero. The issued snapshot retains normalized options and issue date alongside exact PDF bytes. Preprinted output excludes the reference artwork, repeats patient fields/signature/date on additional sheets, and rejects fields/instructions too large to fit; it never silently truncates them. Current address is bound by the preview patient version. All layouts repeat patient identification on continuation pages; preprinted sheets include page/total numbering. POST `/prescription/calibration/` requires authentication/export permission and accepts only paper settings for a patient-free PDF with physical alignment crosses and a 50 mm ruler; it neither issues a clinical document nor consumes a visit preview.

Prescription history GET `/prescription/patient/{id}/history/` returns `{items,total,offset,limit}` (20/page), newest first; optional `visit_id` must belong to that patient. GET `/prescription/documents/{id}/pdf/` returns the exact retained bytes/checksum; `/instructions/` renders a separate A4 patient handout from the issued snapshot without modifying it or issuing another document. All three require current clinical-view/export grants and shared patient/visit scope, accept prescription documents only, and return `Cache-Control: no-store`. Existing copies remain readable during an amendment; revoked access is rechecked on every read. Handouts reproduce free-text directions without parsing a schedule or inferring duration.

Clinical workspace GET `/prescription/visit/{id}/handover/` returns a curated latest signed revision; `/handover/pdf/` renders it with identity, revision and signing date. Patient `/prescription/patient/{id}/handover/` selects the latest approved encounter, optionally excluding the current visit. Handover and approved-risk selection order the latest revision of each encounter by its signed snapshot date; unsigned date changes cannot reorder approved history. Existing ties remain explicit: signing time/revision for handover, encounter ID for risk reporting. Current scope and the clinical-view grant protect JSON reference reads; PDF handovers additionally require export permission. Unsigned amendment facts cannot enter these reads. `clinical_data.instruction_acknowledgement` is optional in working visits: timezone-aware nonfuture `explained_at`, recipient patient/representative/both, optional name/notes and nullable boolean `clarification_needed`. The service stamps recorder/time, ignores forged metadata and preserves unchanged server stamps. Ordinary opening-version, clinician signing and amendment rules apply; acknowledgements enter immutable revisions with the existing JSON field, requiring no schema change.

## Retention and completed review

Archive retains clinical/profile/team/document/action history; new operational writes require active parents. Draft deletion retires and detaches its pending follow-up while retaining occurrence history; finalized history cannot be deleted ordinarily. Pseudonymization clears mutable identity/registers but signed snapshots/corrections/merge/audit can still identify the person: it is not complete erasure. No automatic patient purge duration introduced. Full authenticated ZIP recovery is distinct from catalog merge; raw validated restore deliberately bypasses ordinary ORM history guards.
